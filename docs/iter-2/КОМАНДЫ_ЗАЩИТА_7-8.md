## 2. Работа № 7: один автоматический сценарий

Запустить:

```bash
uv run --locked python scripts/verify_lab7.py
```

Скрипт сам выполняет все пункты работы № 7:

1. создаёт тестового пользователя;
2. вызывает `POST /orders/create`;
3. проверяет путь `OrderPaid → Outbox → RabbitMQ → кухня + доставка`;
4. повторно отправляет событие и проверяет `duplicate: true`;
5. отправляет битое сообщение в DLQ;
6. блокирует доступных курьеров и проверяет Saga;
7. останавливает основной RabbitMQ и проверяет Outbox;
8. запускает RabbitMQ и проверяет повторную публикацию.

После запуска достаточно показать преподавателю вывод `PASS` и сказать, какой критерий он подтверждает. Скрипт специально изменяет основной стек: временно останавливает RabbitMQ и блокирует курьеров. В конце он восстанавливает брокер и курьеров. Тестовые записи остаются в основной базе.

### Что открыть после запуска скрипта

Положительный маршрут:

- kitchen queue: http://localhost:15672/#/queues/%2F/kitchen_queue
- delivery queue: http://localhost:15672/#/queues/%2F/delivery_queue

DLQ:

- kitchen DLQ: http://localhost:15672/#/queues/%2F/kitchen_dlq
- delivery DLQ: http://localhost:15672/#/queues/%2F/delivery_dlq
- compensation DLQ: http://localhost:15672/#/queues/%2F/compensation_dlq

Очередь может показывать `0` после успешной обработки: это означает, что consumer забрал сообщение и подтвердил его через `ack`. Битые сообщения остаются в DLQ.

Скрипт в конце печатает готовую SQL-команду. Её нужно скопировать и выполнить, чтобы показать заказы, Outbox, кухню, доставку и компенсацию:

```bash
docker compose exec -T db psql -U sirius -d sirius_food -c "SELECT id, user_id, status FROM orders ORDER BY id DESC LIMIT 3; SELECT id, routing_key, published FROM outbox_events ORDER BY id DESC LIMIT 10; SELECT * FROM order_compensations ORDER BY order_id DESC LIMIT 3;"
```

### Что говорить по работе № 7

- `POST /orders/create` считается оплатой с баланса и создаёт `OrderPaid`.
- Outbox сохраняет событие в той же транзакции, что заказ и баланс.
- Publisher отправляет событие в exchange `sirius_events`.
- `kitchen_queue` и `delivery_queue` получают одно событие независимо.
- `processed_events` защищает от повторной обработки.
- DLQ хранит сообщения, которые consumer не смог провалидировать.
- Saga возвращает деньги и отменяет заказ, если курьер недоступен.
- Если RabbitMQ падает, событие остаётся в Outbox и отправляется после восстановления.

## 4. Показ SSR, 404 и CSR

Автоматическая проверка:

```bash
./check.sh
```

Ожидаемый результат:

```text
Итог: PASS=7 FAIL=0
```

SSR-проверка: блюда уже есть в HTML до выполнения JavaScript:

```bash
curl -s http://localhost:3000/menu | grep -o 'Борщ сириусский' | head
curl -s http://localhost:3000/menu/2 | grep -o 'Борщ сириусский' | head
```

404 карточки:

```bash
curl -I http://localhost:3000/menu/999999
```

CSR-проверка: в исходном HTML блюда нет:

```bash
curl -s http://localhost:3000/menu-csr | grep -q 'Борщ сириусский' \
  && echo 'CSR содержит блюдо' \
  || echo 'CSR загружает блюдо после запуска JavaScript'
```

## 5. Где находятся метатеги

Общие метаданные находятся в:

```text
sirius-food-frontend/src/app/layout.tsx
```

Там задаются общий `title`, `description` и `metadataBase`.

Метаданные конкретного блюда находятся в:

```text
sirius-food-frontend/src/app/menu/[id]/page.tsx
```

Функция `generateMetadata()` создаёт `title`, `description` и `openGraph.title` для конкретной карточки.

Показать реальные метатеги в HTML:

```bash
curl -s http://localhost:3000/menu/2 \
  | grep -Eo '<title>[^<]+</title>|<meta name="description"[^>]+>|<meta property="og:title"[^>]+>'
```

Ожидаемый результат содержит примерно:

```html
<title>Борщ сириусский · Сириус.Еда</title>
<meta name="description" content="Борщ сириусский — 120 ₽ в Сириус.Еде"/>
<meta property="og:title" content="Борщ сириусский"/>
```

## 7. ISR и сравнение SSR/CSR

ISR задан в страницах:

```text
sirius-food-frontend/src/app/menu/(list)/page.tsx
sirius-food-frontend/src/app/menu/[id]/page.tsx
```

Обе страницы используют `revalidate = 60`.

На защите объяснить сценарий:

1. открыть карточку блюда;
2. изменить цену через API под ролью повара;
3. сразу обновить страницу — может отображаться старая кешированная версия;
4. подождать 60 секунд;
5. обновить страницу и увидеть новую цену.

Для замеров:

1. открыть DevTools → Network;
2. включить `Disable cache`;
3. трижды открыть `/menu`;
4. трижды открыть `/menu-csr`;
5. записать время до первого блюда;
6. объяснить, что SSR отдаёт блюдо в HTML, а CSR загружает его браузером.

Готовые локальные замеры находятся в [ВИТРИНА_NEXTJS.md](ВИТРИНА_NEXTJS.md).
