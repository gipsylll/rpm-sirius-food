# Защита лабораторной работы № 9

## Тема работы

**Observability: логи, метрики и распределённая трассировка в «Сириус.Еде».**

Цель работы — сделать систему наблюдаемой: по одному идентификатору найти путь заказа через API, Outbox, RabbitMQ, кухню и доставку, а также посмотреть состояние системы по логам, метрикам и трассам.

## Короткий ответ для начала защиты

> В работе реализованы три столпа observability: структурированные JSON-логи, метрики Prometheus/Grafana и распределённая трассировка OpenTelemetry/Jaeger. Каждый HTTP-запрос получает `correlation_id` из заголовка `X-Correlation-ID` или новый UUID. Этот идентификатор возвращается клиенту, сохраняется в Outbox, передаётся через RabbitMQ и появляется в логах publisher, кухни и доставки. Метрики доступны на `/metrics`, Prometheus собирает их, а Grafana показывает RPS, p95 и состояние очередей. OpenTelemetry передаёт trace context через Outbox и RabbitMQ, поэтому один заказ можно открыть в Jaeger как распределённый trace.

## Три столпа observability

| Столп | На какой вопрос отвечает | Пример |
|---|---|---|
| Логи | Что произошло? | `order_created`, `event_processed` |
| Метрики | Как система себя чувствует? | RPS, p95, ошибки, очередь |
| Трассировка | Где прошёл запрос? | API → publisher → kitchen → delivery |

`correlation_id` связывает бизнес-операцию в логах и базе. `trace_id` связывает технические spans в Jaeger. Это разные идентификаторы: один заказ может иметь несколько технических trace, но общий correlation ID.

## Как проходит correlation ID

```text
X-Correlation-ID от клиента
        |
        v
HTTP middleware API
        |
        +--> JSON-лог API
        |
        +--> outbox_events.correlation_id
        |
        v
RabbitMQ headers
        |
        +--> publisher
        +--> kitchen consumer
        +--> delivery consumer
        +--> compensation consumer
```

## Какие файлы показывать

### Middleware и JSON-логи

Файл: `app/core/observability.py`.

Показать чтение `X-Correlation-ID`, проверку длины и печатаемости, генерацию UUID, `ContextVar`, возврат ID в response header, Prometheus counters/histogram и функцию `log()`.

Пример лога:

```json
{
  "event": "event_processed",
  "correlation_id": "lab9-final-42",
  "consumer": "kitchen",
  "order_id": 37,
  "duplicate": false
}
```

Что сказать:

> JSON удобен для поиска и агрегации: можно выбрать все записи с конкретным `correlation_id`, `order_id` или `consumer`.

### Сохранение ID в Outbox

Файлы:

```text
app/modules/orders/repository.py
app/events/common.py
app/models.py
```

В `OutboxEvent` сохраняются `id`, `routing_key`, `payload`, `correlation_id`, `trace_context` и `published`.

> Correlation ID не теряется после завершения HTTP-запроса: он записывается в Outbox вместе с событием и используется фоновой публикацией.

### Publisher и consumer’ы

Файлы:

```text
app/events/publisher.py
app/events/consumer.py
```

Publisher добавляет ID и trace headers в RabbitMQ message headers. Consumer читает заголовки и устанавливает контекст перед обработкой.

Основные JSON-события: `http_request`, `order_created`, `event_published`, `event_processed`, `event_rejected`, `publisher_retry`, `consumer_reconnect`.

### Prometheus

Метрики API реализованы в `app/core/observability.py` и доступны по адресу:

```text
GET http://localhost:8000/metrics
```

Основные метрики:

```text
sirius_http_requests_total
sirius_http_request_duration_seconds
```

Конфигурация сбора находится в `monitoring/prometheus.yml`. Prometheus собирает API и RabbitMQ.

### Grafana

Dashboard находится в `monitoring/grafana/dashboards/sirius.json` и показывает:

- HTTP requests per second;
- HTTP p95 latency;
- количество сообщений в RabbitMQ.

Адрес: `http://localhost:3001`, логин и пароль: `admin / admin`.

### OpenTelemetry и Jaeger

Файл: `app/core/tracing.py`.

В `docker-compose.yml` для API и event-сервисов задан OTLP endpoint `http://jaeger:4318/v1/traces`.

Сервисы имеют имена:

```text
sirius-api
sirius-publisher
sirius-kitchen
sirius-delivery
sirius-compensation
```

Jaeger: `http://localhost:16686`.

> HTTP middleware создаёт серверный span. Publisher и consumer создают свои spans и продолжают контекст, сохранённый в Outbox и RabbitMQ headers. Поэтому в Jaeger видна распределённая цепочка обработки заказа.

### Sentry

Интеграция находится в `app/core/tracing.py`, `app/main.py` и `scripts/verify_sentry.py`.

Sentry включается только при наличии `SENTRY_DSN`. Correlation ID записывается в Sentry tag. Тестовый endpoint включается только при `SENTRY_TEST_ENABLED=1`:

```text
GET /__debug__/sentry
```

## Живая демонстрация correlation ID

Создать заказ через Swagger или авторизованный запрос. В заголовке указать:

```text
X-Correlation-ID: lab9-final-42
```

Посмотреть логи:

```bash
docker compose logs --since=2m --no-color api event_publisher kitchen delivery_events \
  | grep lab9-final-42
```

Нужно показать записи API (`http_request`/`order_created`), publisher (`event_published`), кухни и доставки (`event_processed`).

> Один и тот же correlation ID прошёл через HTTP, Outbox, RabbitMQ и consumer’ы. Это позволяет расследовать заказ без поиска по времени или случайному тексту.

## Проверка Jaeger

1. Создать заказ с `X-Correlation-ID`.
2. Открыть `http://localhost:16686`.
3. В **Service** выбрать `sirius-api`.
4. Нажать **Find Traces**.
5. Открыть операцию `POST /orders/create`.
6. Показать spans API, publisher, kitchen и delivery.

`GET /menu/items` не создаёт событий кухни и доставки, поэтому для полного trace нужно создать заказ. Jaeger хранит данные в памяти и теряет старые traces после перезапуска.

## Проверка Sentry

Реальная отправка требует DSN проекта. В корневом `.env` добавить:

```text
SENTRY_DSN=<DSN проекта>
```

Затем выполнить:

```bash
uv run --locked python scripts/verify_sentry.py
```

Скрипт пересоздаёт API, отправляет ошибку с `X-Correlation-ID: sentry-demo`, проверяет HTTP 500 и выключает тестовый endpoint. В Sentry нужно найти `Sirius Food Sentry test` и tag `correlation_id=sentry-demo`.

Без DSN код интеграции есть, но реальная доставка события во внешний Sentry не подтверждена.

## Типовые вопросы

### Чем correlation ID отличается от trace ID?

Correlation ID — бизнес-идентификатор, который задаём мы и сохраняем в логах и базе. Trace ID создаёт OpenTelemetry для технического distributed trace.

### Почему логи пишутся в stdout?

Docker и системы сбора логов автоматически читают stdout контейнера. Файлы внутри контейнера могут исчезнуть при пересоздании.

### Что показывает Prometheus?

Prometheus хранит временные ряды: количество запросов, latency, ошибки и состояние очередей.

### Зачем нужен Grafana?

Prometheus хранит метрики, а Grafana визуализирует их на dashboard.

### Что такое span?

Span — один измеряемый шаг операции. Несколько связанных spans образуют trace.

### Что будет, если consumer работает после HTTP-запроса?

Trace context сохраняется в Outbox и передаётся через RabbitMQ headers, поэтому фоновые spans можно связать с исходным заказом.
