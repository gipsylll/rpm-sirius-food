# Защита лабораторной работы № 10

## Тема работы

**Тестирование, нагрузочное тестирование, контрактная проверка и CI.**

Цель работы — проверить систему на разных уровнях: unit, integration, contract и нагрузочными сценариями, а также запускать тесты автоматически в GitHub Actions.

## Короткий ответ для начала защиты

> В работе используется пирамида тестов. Unit-тесты быстро проверяют бизнес-логику изолированно, интеграционный тест проверяет создание заказа с реальной PostgreSQL в Testcontainers, контрактный тест Pact проверяет формат события `OrderPaid`, а Locust создаёт виртуальную нагрузку и показывает RPS, latency и ошибки. Mutmut меняет код и проверяет, ловят ли тесты искусственные ошибки. GitHub Actions запускает полный pytest-набор на push и pull request.

## Требования работы

Для базового уровня нужны:

1. интеграционный тест с Testcontainers и чистой PostgreSQL;
2. сценарий Locust для меню и заказов;
3. нагрузка примерно 50–200 пользователей;
4. найденное узкое место по метрикам ресурсов;
5. GitHub Actions на push и pull request;
6. проверка зелёного CI и блокировки merge при красном CI.

Для 9–10 баллов нужны оба бонуса:

- Pact;
- mutmut.

## Пирамида тестов

```text
              E2E
           Integration
       Contract / component
             Unit
```

Чем выше уровень, тем тест медленнее и дороже. Поэтому unit-тестов много, интеграционных меньше, а E2E и нагрузочные сценарии запускаются отдельно.

## Какие файлы показывать

### Unit-тесты

```text
tests/test_orders_service.py
tests/test_menu_service.py
tests/test_delivery_service.py
```

Проверяются списание баланса, недоступное блюдо, недостаточный баланс, отмена заказа, IDOR, права повара и правила доставки.

### Интеграционный Testcontainers-тест

Файл: `tests/integration/test_postgres_orders.py`.

Тест поднимает чистый контейнер `postgres:15`, передаёт URL через `DATABASE_URL`, выполняет `alembic upgrade head`, создаёт пользователя и блюдо, вызывает `POST /orders/create`, проверяет заказ, баланс, Outbox и `X-Correlation-ID`, а после теста удаляет контейнер.

> Testcontainers даёт чистую временную базу нужной версии. Тесты не используют общие данные и не зависят от состояния основной базы.

Запуск:

```bash
uv run --locked pytest -q tests/integration -v
```

### Locust

Файл: `locustfile.py`.

Сценарий содержит 70% запросов списка меню, 20% запросов карточки блюда и 10% создания заказа при наличии `LOCUST_TOKEN`. Пауза пользователя — `between(1, 3)`.

Запуск с UI:

```bash
uv run --locked locust -f locustfile.py --host=http://127.0.0.1:8000
```

Открыть `http://localhost:8089`.

Без токена сценарий безопасно тестирует чтение. Для создания заказов:

```bash
export LOCUST_TOKEN='<JWT пользователя с балансом>'
export LOCUST_ITEM_ID=1
```

Заказы списывают баланс, поэтому нужны тестовые данные.

## Найденное узкое место

Во время прогона на 1000 пользователей были сняты ресурсы Docker:

```text
rpm_api       CPU около 68%
rpm_db        CPU около 5%
rpm_redis     CPU около 1,4%
rpm-rabbitmq  CPU около 1,6%
```

Наиболее нагружен API-контейнер. При росте нагрузки p95 увеличился с 36 до 4800 мс, а появились ошибки `RemoteDisconnected`.

Фраза для защиты:

> Узкое место — CPU и пропускная способность API-процесса, а не PostgreSQL, Redis или RabbitMQ. При 50–500 пользователях система работает без ошибок, а при 1000 пользователях API перегружается и закрывает часть соединений. Следующий шаг оптимизации — несколько worker-процессов API, настройка connection pool и профилирование menu endpoints.

Метрики API:

```bash
curl -s http://localhost:8000/metrics \
  | grep -E 'sirius_http_requests_total|sirius_http_request_duration_seconds'
```

## CI в GitHub Actions

Файл: `.github/workflows/tests.yml`.

Workflow запускается на:

```yaml
on: [push, pull_request]
```

Шаги — checkout, Python 3.11, установка uv, `uv sync --locked`, `uv run --locked pytest -q`.

Локальная команда CI:

```bash
uv sync --locked
uv run --locked pytest -q
```

Текущий локальный результат:

```text
61 passed, 19 warnings
```

## Ограничение по CI

Локальный репозиторий сейчас не подключён к GitHub remote, поэтому здесь нельзя честно подтвердить реальный зелёный workflow, красный workflow после поломки теста и branch protection. Workflow в репозитории настроен.

Для полного внешнего подтверждения:

1. подключить remote и запушить `main`;
2. открыть GitHub Actions и показать зелёный запуск;
3. во временной ветке добавить `assert False`, показать красный запуск;
4. включить в Branch protection обязательную проверку `Tests`;
5. показать, что merge заблокирован при красном статусе;
6. удалить временную поломку.

## Pact

Файл: `tests/contract/test_pact_order_paid.py`.

Контракт проверяет сообщение `OrderPaid` с полями:

```text
event_id, order_id, user_id, item_id,
quantity, total, currency
```

Положительный provider verification проходит. Затем тест намеренно меняет `total` на `amount` и ожидает падение.

Запуск:

```bash
uv run --locked pytest -q tests/contract -v
```

Результат:

```text
1 passed
```

> Pact защищает границу между publisher и consumer. Изменение формата сообщения обнаруживается до production.

## Mutmut

Конфигурация находится в `pyproject.toml`:

```toml
[tool.mutmut]
source_paths = ["app/modules/orders/service.py"]
pytest_add_cli_args_test_selection = ["tests/test_orders_service.py"]
```

Запуск:

```bash
uv run --locked mutmut run
uv run --locked mutmut results
```

Последний результат:

```text
Всего мутаций: 158
Убито: 96
Выжило: 62
Непокрытых тестами: 0
```

После усиления тестов добавлены проверки отмены владельцем, сотрудником, чужим пользователем, повторной отмены, отсутствующего заказа, некорректного количества и бизнес-правил.

> Выжившая мутация означает, что тесты не заметили искусственное изменение. В текущем запуске непокрытых мутаций нет, а 96 из 158 мутаций убиты. Остальные в основном относятся к fallback-значениям и аргументам фоновых уведомлений.

## Контрольные вопросы

### Чем unit-тест отличается от интеграционного?

Unit-тест проверяет отдельный компонент изолированно. Интеграционный тест проверяет взаимодействие компонентов и настоящую PostgreSQL в контейнере.

### Зачем Testcontainers?

Чтобы каждый запуск получал чистую временную базу нужной версии и не зависел от общей базы или старых данных.

### Что такое p95?

95% запросов выполняются быстрее значения p95. Если p95 растёт, система начинает отвечать медленнее для заметной части пользователей.

### Почему нагрузочный тест нужно связывать с Grafana?

Locust показывает, что latency выросла. Prometheus и Grafana помогают понять, какой ресурс перегружен.

### Что такое Pact?

Pact — consumer-driven contract test. Consumer описывает ожидаемый формат сообщения, а provider проверяет совместимость.

### Что значит «мутация выжила»?

Mutmut изменил код, но тесты всё равно прошли. Значит, тесты не обнаруживают конкретную искусственную ошибку.

### Почему покрытие строк не гарантирует качество тестов?

Строка может выполниться, но тест не проверить правильный результат. Mutation testing проверяет способность тестов ловить изменения поведения.

### Что должно происходить при красном CI?

Pull request нельзя вливать до исправления причины падения. Для этого в GitHub branch protection required status check должен быть обязательным.

> В работе реализована многоуровневая проверка системы: unit-тесты, Testcontainers, Pact, mutmut и Locust. Все локальные тесты проходят, контракт проверяется положительно и отрицательно, а нагрузочный прогон показал границу системы: при 1000 виртуальных пользователях перегружается API и растёт p95.
