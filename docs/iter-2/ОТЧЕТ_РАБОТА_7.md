# Практическая работа № 7 — Event-driven архитектура

## Что требовалось

По методичке нужно было реализовать:

- публикацию события OrderPaid после оплаты заказа;
- независимую обработку события кухней и доставкой;
- идемпотентность consumer’ов;
- Dead Letter Queue для некорректных сообщений;
- Saga-компенсацию при отсутствии курьера;
- Transactional Outbox, чтобы событие не терялось при падении RabbitMQ.

## Архитектура

    POST /orders/create

       одна транзакция

## Положительный сценарий

Нормальная отправка запускается ручкой POST /orders/create. В этом проекте создание заказа считается оплатой с баланса.

Сначала API:

1. достаёт пользователя из JWT;
2. проверяет блюдо и баланс;
3. уменьшает баланс;
4. создаёт заказ;
5. создаёт OrderPaid в Outbox;
6. фиксирует заказ, баланс и событие одной транзакцией.

Publisher читает outbox_events с published=false и отправляет сообщение в exchange sirius_events с routing key order.paid.

Одно событие приходит в две независимые очереди:

    order.paid → kitchen_queue  → consumer кухни
    order.paid → delivery_queue → consumer доставки

## Файлы реализации

Общая логика и объявления очередей:

    app/events/common.py

Publisher:

    app/events/publisher.py

Consumer кухни, доставки и компенсации:

    app/events/consumer.py

Compatibility-модуль для старых импортов и тестов:

    app/events/worker.py

Docker Compose запускает отдельные процессы:

    event_publisher → python -m app.events.publisher
    kitchen         → python -m app.events.consumer kitchen
    delivery_events → python -m app.events.consumer delivery
    compensation    → python -m app.events.consumer compensation

RabbitMQ-часть использует aio-pika. Публикация и чтение сообщений асинхронные, publisher ждёт broker confirm, а consumer использует async iterator и reconnect.

Синхронные SQL-транзакции consumer’ов выполняются через asyncio.to_thread, чтобы не блокировать event loop. Kombu остаётся только внутренней зависимостью Celery.

## Идемпотентность

RabbitMQ гарантирует доставку как минимум один раз, поэтому сообщение может прийти повторно.

Для защиты используется таблица processed_events с составным ключом:

    consumer + event_id

Перед обработкой consumer проверяет:

    if db.get(ProcessedEvent, (name, event_id)):
        return False

При повторной доставке:

- в кухне не создаётся второй KitchenOrder;
- в доставке не создаётся вторая Delivery;
- компенсация не выполняется повторно;
- сообщение подтверждается через ack.

Кухня и доставка обрабатывают одно событие независимо: для них создаются разные записи consumer + event_id.

## Dead Letter Queue

Настроены очереди:

    kitchen_queue      → kitchen_dlq
    delivery_queue     → delivery_dlq
    compensation_queue → compensation_dlq

Если сообщение не проходит валидацию OrderPaid или содержит некорректный JSON, consumer:

1. пишет event_rejected в JSON-лог;
2. делает reject(requeue=false);
3. RabbitMQ отправляет сообщение в соответствующую DLQ.

Ссылки:

- http://localhost:15672/#/queues/%2F/kitchen_dlq
- http://localhost:15672/#/queues/%2F/delivery_dlq
- http://localhost:15672/#/queues/%2F/compensation_dlq

## Saga-компенсация

Если delivery consumer не находит доступного курьера, он создаёт событие:

    delivery.failed

Compensation consumer:

1. блокирует пользователя через SELECT FOR UPDATE;
2. находит исходный OrderPaid;
3. возвращает сумму на баланс;
4. меняет статус заказа на cancelled;
5. создаёт order_compensations;
6. публикует order.cancelled.

Таблица order_compensations использует order_id как первичный ключ, поэтому один заказ нельзя компенсировать дважды.

## Transactional Outbox

Без Outbox возможен сценарий:

    баланс списан → RabbitMQ недоступен → событие потеряно

С Outbox заказ, баланс и OrderPaid сохраняются одной транзакцией.

В outbox_events хранятся:

- id;
- routing_key;
- payload;
- correlation_id;
- trace_context;
- published.

Если RabbitMQ выключен, событие остаётся с published=false. После восстановления publisher отправляет его и меняет published на true.

Положительный сценарий объясняется так:

    POST /orders/create
    → Transactional Outbox
    → RabbitMQ exchange
    → kitchen_queue и delivery_queue

После этого объясняются три отказоустойчивых сценария:

- повторное сообщение → processed_events;

- нет курьера → Saga-компенсация;
- RabbitMQ недоступен → событие остаётся в Outbox.

Короткий ответ для защиты:

> После создания заказа API атомарно сохраняет заказ, списание и OrderPaid в Transactional Outbox. Асинхронный publisher отправляет событие в RabbitMQ. Кухня и доставка получают его из независимых очередей. Повторная доставка безопасна благодаря processed_events. Битые сообщения попадают в DLQ. Если курьер недоступен, Saga возвращает деньги и отменяет заказ. Если RabbitMQ недоступен, событие остаётся в Outbox и публикуется после восстановления брокера.
